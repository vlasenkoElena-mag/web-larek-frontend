```typescript
export class AppStateModel implements AppState {
    // интерфейс API передается в конструктор
	constructor(protected api: IFilmAPI, protected settings: AppStateSettings) {}

	// метод загрузки movies использующий API
	async loadMovies(): Promise<void> {
		this.movies.clear();
		const movies = await this.api.getFilms();
		for (const movie of movies) {
			this.movies.set(movie.id, movie);
		}
		this.notifyChanged(AppStateChanges.movies);
	}

    // метод загрузки schedule использующий API
	async loadSchedule(id: string): Promise<void> {
		if (!this.movies.has(id)) {
			throw new Error(`Invalid movie id: ${id}`);
		}
		this.movieSessions.clear();
		for (const session of await this.api.getFilmSchedule(id)) {
			this.movieSessions.set(session.id, session);
		}
		this.notifyChanged(AppStateChanges.sessions);
	}

    // еще метод использующий API
	async orderTickets(): Promise<OrderResult[]> {
		try {
			const result = await this.api.orderTickets(this.order);
			this.basket.clear();
			this.selectSession(null);
			this.movieSessions.clear();
			this.persistState();
			this.notifyChanged(AppStateChanges.basket);
			return result;
		} catch (err: unknown) {
			if (err instanceof Error) {
				this.setMessage(err.message, true);
			}
			if (typeof err === 'string') {
				this.setMessage(err, true);
			}
			return [];
		}
	}
	//...
}
```

## Пункт 2: Разделение моделей
```
"Список покупок и операции с корзиной стоит вынести в отдельную модель. В модели заказа оставьте только описание покупателя - данные о доставке и контакты."
```
```
"Стоит разбить функционал на три модели: продукты, корзина покупок и покупатель (Заказ). 
Корзину покупок можно вынести как самостоятельный модуль системы, который опишет действия изменения состава покупок, а также расчета стоимости, количества товаров в корзине, проверку на наличие товара в корзине"
```

На первый взгляд это кажется логичным, но:
- В API не представлены никакие сущности кроме заказа (order) и продукта (product).
- Как мы видим в шаблонах Figma и описании API бэкенда, данные используются вместе.

Все, что мы получим, разбив модель на части — это необходимость снова собирать их вместе. Кроме того, это повлечет необходимость вводить дополнительный класс-посредник для сбора данных из разных моделей, отправки их в API, обработки и публикации результатов. Вы предлагаете на роль посредника презентер, так как считаете, что это его ответственность, но это уже разобрано выше.

Если же предположить, что с API может работать модель (как в эталонном примере и классическом описании MVP), то целостность OrderModel выглядит вполне оправданной. Можно выделить отдельные классы для Cart, OrderDetails и Contacts, агрегированные в OrderModel, но у них не будет поведения (кроме класса Cart). Туда можно было бы поместить логику валидации, но планировалось валидировать данные в представлении форм и публиковать презентеру уже валидные данные. Таким образом, эти классы будут просто контейнерами с данными, для чего проще использовать простые литералы (как сейчас).

```
Предполагается, что данные покупателя должны проходить валидацию. Добавьте здесь соответствующий метод
```
Добавила валидацию в модели, но она не проверяет значения (это будет в валидации форм), а только сам факт того, что данные установлены.

## Пункт 3: Наследование в представлениях
```
Учитывайте в реализации, что класс модального окна не должен являться родителем другим классам, и не может быть расширен другими классами. 
Модальное окно описывает только кнопку Закрыть, слой "Оверлей" (затемнение вокруг) и контейнер для контента. В контейнер будут рендерится другие блоки - формы, корзина, успех. Примерно вот так modal.open(basketView.render())
```

Не очень понятно, о чем идет речь, так как этот комментарий указан относительно FormModalView.
```typescript
type FormModalView<T extends object> = FormView<T> & ModalView;
```
Это абстрактное описание типа представления, реализация которого на данном этапе отсутствует и заданием не предусматривается.

Все, что здесь написано:
- FormModalView — тип представления модального окна с формой.
- Методы: 
    show(): void, 
    hide(): void.
- Публикуемые события: 'FORM_SUBMIT' с данными формы в качестве Payload.

Реализация данного представления через класс с наследованием от ModalView не планировалось. Скорее планировалось что-то вроде:
```typescript
class FormModalView {
    #modal: ModalView;
    #form: HTMLFormElement;
    #ee: EventEmitter<FromEvents>;

    constructor(...) {
        ...
        this.#form.addEventListener('submit', () => {
            this.#ee.emit('FORM_SUBMIT', this.#getFormDate());
        })
    }

    show() {
        this.#modal.show();
    }

    hide() {
        this.#modal.hide();
    }

    #getFormDate() {
        //... логика извлечения данных из формы
    }
}
```
Возможно, он будет наследовать от класса Observable или EventEmitter (содержащего логику публикации/подписки), но вряд ли от ModalView. Данный этап не предполагает реализацию проекта целиком; сейчас для завершения проекта не хватает только логики представлений и API. Так как API очень небольшое, то написание реализации представлений практически эквивалентно написанию проекта целиком.

Также отмечу, что хотя и не планировалось наследоваться от ModalView, но такое решение не является, на мой взгляд, критической ошибкой. Наследование описывает отношения вида 'is a' (является), и вполне допустимо считать, что модальное окно с формой является модальным окном.
